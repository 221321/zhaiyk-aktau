# Автотесты

## Зачем это нужно

До сих пор каждую фичу проверяли вручную — руками писали curl-команды,
смотрели на ответ, потом всё стирали. Это работает, но есть две дыры:

1. Проверяются только сценарии, которые придумал я в моменте. Реальный
   пользователь почти всегда находит то, что не пришло в голову — например,
   баг с весом (10.09): «Исправить доставленное количество» принимало
   любое число, но молча срезало его обратно, если оно было БОЛЬШЕ
   исходного — ни одна ручная проверка это не поймала, пока админ не
   прислал видео с реальной попыткой.
2. Когда код меняется в одном месте, ничто не перепроверяет автоматически,
   не сломалось ли что-то в другом — только если сам вспомнишь.

Автотест — тот же самый ручной сценарий («создать заявку, доставить,
проверить остаток»), но записанный один раз и сохранённый в проекте
навсегда. `npm test` прогоняет их все за пару секунд. Если правка что-то
задевает — тест падает ДО того, как код уйдёт в PR, а не после того, как
это найдут на проде.

## Как устроено

- `node --test` — встроенный в сам Node.js тестраннер, без сторонних
  зависимостей (Jest и т.п. не нужны).
- Каждый тестовый файл поднимает **настоящий** `server.js` отдельным
  процессом на своём порту, с изолированной базой (`DB_PATH`) и папкой
  загрузок (`UPLOADS_DIR`) во временной директории — это не моки, тесты
  ходят по HTTP так же, как реальный браузер, и ничего не трогают в
  боевом `db.json`/`uploads/`.
- Общий код (поднять сервер, залогиниться под сидовым пользователем,
  завести товар с остатком, довезти заявку) вынесен в `tests/helpers.js`,
  чтобы каждый файл не повторял один и тот же бойлерплейт.

## Запуск

```bash
npm test
```

## Что уже покрыто

- `tests/orders.test.js` — создание заявки резервирует остаток (не
  списывает), доставка списывает окончательно, нельзя заказать больше
  доступного, доставку нельзя подтвердить без обязательных фото.
- `tests/prices.test.js` — свободная правка цены только у admin, работает
  до статуса «Доставлено» включительно, отрицательная цена отклоняется,
  после `revoked` менять нельзя.
- `tests/items-edit.test.js` — правка состава заявки в статусе «Ожидает»:
  доступ только владельцу/admin, лимит остатка с учётом собственного
  резерва заявки, блокировка вне статуса `new`, снова доступна после
  «вернуть в очередь».
- `tests/delivered-items.test.js` — регресс-тест на баг с весом: можно и
  уменьшить, и увеличить доставленное количество выше исходного, остаток
  на складе пересчитывается правильно в обе стороны.
- `tests/stock-sync.test.js` — синк остатков (`/api/stock/sync`) не
  обнуляет коды, отсутствующие в конкретном пакете (1С может слать не
  полный снимок); синк номенклатуры (`/api/products/sync`) — наоборот,
  всегда полный снимок, поэтому пропавший код там обнуляет остаток;
  дубль кода в одном пакете не создаёт вторую позицию в каталоге.

## Чего здесь принципиально нет

Не гонимся за 100% покрытием — это раздувает время на разработку без
пропорциональной пользы. Покрыты в первую очередь **деньги и остаток**:
заявки, синки с 1С, правки задним числом. UI (React-часть в
`public/src/app.jsx`) и второстепенные отчёты автотестами пока не
покрыты — для них по-прежнему ручная проверка через браузер/видео, как и
раньше.

## Когда добавлять новый тест

Не обязательно на каждую фичу — но правило простое: **если баг был
неочевидным и мог случиться снова** (как с весом), тест на него стоит
времени. Если баг был разовой опечаткой в конкретном месте — чинить и
идти дальше, тест не обязателен.
